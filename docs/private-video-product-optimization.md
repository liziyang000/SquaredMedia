# 私人视频收藏与播放系统产品优化报告

最后核验：2026-07-23

文档状态：当前产品优化基线

适用范围：React 前台、`pingfangapi`、MacCMS 内容与用户数据、原生播放器承载页、视频库维护工具。

本文用于指导后续产品设计、交互设计、接口设计和开发排期。它不是单个功能的详细实现方案；进入开发前，应从本文拆出范围明确的任务，并补充接口、异常状态、测试和验收说明。可以独立完成的小功能继续记录在根目录的 [TODOList](../TODOList.md)。

## 审查范围与事实边界

本次审查基于：

- 当前 React staging 的桌面端和 390px 移动端页面。
- 同版本本地环境中的登录、详情、收藏、历史和播放器流程。
- `apps/web/`、`addons/pingfangapi/`、现有测试和仓库文档。

以下边界必须保留：

- 真实 staging 的受保护详情和播放器未完成全部会员、线路和媒体源矩阵验收。
- 当前没有服务器 CPU、内存和磁盘的实时监控证据；本文中的服务器规格是目标，不是现状结论。
- 浏览器请求数和接口耗时是本次单次审查样本，用于定位问题，不等同于长期 p95。
- 不分析 SEO、搜索排名、广告、商业化、用户增长或营销转化。
- 不以产品优化为理由绕过 MacCMS 登录、内容权限或播放器授权。
- 除非用户明确要求，不自动部署任何实现。

## 一、执行摘要

当前网站已经具备较成熟的视觉风格、内容浏览能力和安全的播放授权边界，但整体仍偏向“公共流媒体展示站”。对于私人长期使用，决定体验的“继续观看、跨端进度、收藏管理、个人标签和内容维护”尚未形成完整闭环。

产品目标不是复制商业流媒体，而是组合：

- Netflix 的内容组织方式。
- Plex 和 Jellyfin 的私人媒体库理念。
- Linear 式清晰、克制、可预测的操作效率。

| 内容浏览             |   62 | 分类和海报墙可用，筛选密度、数据一致性和预取存在明显问题 |
| 详情页               |   76 | 核心按钮已收敛，仍需加强续播和移动端信息布局             |

核心判断：

> 降低首页展示感，提高资料库感；降低功能数量感，提高连续使用感。

## 二、网站定位

### 网站定位

一个基于 MacCMS 内容库的私人视频收藏、检索、管理和播放系统。

### 核心用户

网站所有者，以及少量被授权的个人或家庭用户。用户数量不是主要约束，长期积累、跨设备连续使用和低维护成本才是核心。

### 主要场景

1. 打开网站，继续上次没有看完的内容。
2. 搜索已知影片、演员、导演或标签。
3. 浏览最近入库、收藏更新和未看内容。
4. 查看详情并选择剧集、线路播放。
5. 在手机和电脑之间接续播放。
6. 收藏、标记看过、评分或添加私人标签。
7. 在后台处理海报缺失、分类错误、失效片源和重复内容。

### 当前主要流程

```text
首页或搜索
  → 片库、分类或详情
  → 选择剧集和线路
  → 播放
  → 保存记录或收藏
  → 下次从首页、历史或收藏继续
```

当前最后一步没有稳定回到第一步：播放位置没有在所有播放器形态中可靠保存，首页继续观看也没有占据最高优先级。

### 当前优势

- 暗色影院视觉完整，风格统一。
- 海报墙、详情页、分类页已经具备现代内容平台的基本形态。
- MacCMS 继续承担内容、用户、权限和播放器授权，安全边界合理。
- React 前端没有提前暴露或绕过原始播放地址。
- 类型选择后的子分类逻辑已经可用。
- 详情页收藏位于播放按钮旁，评分和顶踩已压缩成一行。
- 下载和评论不再占据详情页主要操作区。
- 加载动效、响应式和减少动态效果支持已有良好基础。

### 当前主要问题

网站优先回答的是“有什么热门内容”，而不是“我接下来最可能做什么”。对于私人系统，这一优先级需要反转。

## 三、产品设计原则

后续开发应遵守以下原则：

1. **连续观看优先。** 有历史时，继续观看必须高于榜单和主推内容。
2. **个人状态独立于公共元数据。** MacCMS 类型、地区和剧情描述内容；标签、未看和已看完描述用户。
3. **一次操作完成高频任务。** 首页到续播不超过一次点击。
4. **能力按来源显示。** 只有播放源真正支持时才显示字幕、清晰度或倍速入口。
5. **不为私人站引入不必要架构。** 不拆微服务，不默认引入 Elasticsearch，不重写 MacCMS。
6. **安全和权限不退让。** 所有播放、收藏和历史写操作继续使用同源会话、CSRF 和后端权限校验。
7. **动画不能阻塞内容。** 动效服务于状态解释和层级切换，不为了播放完整动画而延迟内容可用。
8. **多端同步以账户为主。** 登录后云端状态是权威数据，本地存储只做游客兜底或一次性迁移。

## 四、首页体验

### 当前问题与方案

| -------------------------------------- | -------------------------- | ---------------------------------------------------------- | ------ |
| 继续观看位于英雄区、榜单和分类之后     | 每日最高频操作需要滚动     | 有历史时将继续观看放到首屏第一行                           | P0     |
| 英雄区高度过大                         | 桌面和移动端首屏有效信息少 | 桌面控制在约 360–420px，移动端控制在约 280–320px           | P1     |
| 继续观看只有文字进度，最多展示 4 条    | 无法快速判断进度和剩余时长 | 增加进度条、剩余时间、剧集名称和单条隐藏；桌面展示 4–6 条  | P0     |
| 主导航只有首页和视频                   | 收藏、历史和片库入口过深   | 调整为首页、片库、收藏、历史；分类成为片库内的筛选或菜单   | P1     |
| 移动端搜索在菜单内                     | 搜索多一次操作             | 保留独立搜索入口，或在移动端提供底部搜索入口               | P1     |

| 首页频道英文代码和中文分类存在语义错配 | 影响理解和数据可信感       | 分类语义由后台配置或明确映射驱动，不依赖当前硬编码频道编号 | P0     |
| 所有用户看到相同首页                   | 私人站没有根据个人状态改变 | 根据是否存在历史、收藏和登录状态调整首页区块顺序           | P1     |

### 推荐首页结构

存在观看记录时：

1. 顶部导航和全局搜索。
2. 继续观看。
3. 我的片库：收藏更新、最近入库、未看、已看完。
4. 精简主推内容。
5. 最近更新分类货架。
6. 年度榜单和热门内容。

没有观看记录时：

1. 主推内容。
2. 最近入库。
3. 分类入口。
4. 收藏和标签引导。

可以增加用户偏好：

- 影院模式：保留大幅主视觉。
- 效率模式：直接从继续观看和我的片库开始。

## 五、内容浏览体验

### 分类体系

电影、电视剧、动漫和综艺四个一级分类清楚；选择类型后能够显示相应子类，应继续保留。

当前问题：

- 现有分类主要描述内容，不描述个人状态。
- 本次实测年份筛选只到 2021，但列表存在 2022–2026 内容。
- 首页频道代码与实际分类 ID 的语义存在错配。
- 片库主导航先进入分类卡，再进入全部影片，增加一次操作。

优化方向：

- 公共分类继续使用类型、地区、年份、语言和剧情。
- 私人维度新增未看、在看、已看完、收藏后有更新和自定义标签。
- 主导航中的“片库”直接进入 `/videos`，分类页保留为次级总览。
- 年份选项由真实数据或采集后自动刷新的配置生成。

### 片库列表

当前问题：

- 桌面端首屏几乎被筛选面板占满，海报墙不可见。
- 390px 移动端连续两屏主要仍为筛选选项。
- 本次单次加载观察到 62 个资源请求，其中 45 个是 `fetch`；大量请求来自筛选链接的自动预取。
- 卡片大量显示 0.0 评分。
- 页码适合精确跳转，但不适合在约 13 万内容中日常探索。

优化方案：

- 桌面端将筛选收成一行：类型、地区、年份、更多筛选、当前条件、重置。
- 移动端使用底部筛选面板，页面只保留筛选按钮和生效条件。
- 筛选、年份和分页链接关闭自动预取；详情链接只在悬停或进入视口后预取。
- 没有有效评分时隐藏 0.0。
- 保留页码，同时提供“继续加载”。
- 支持保存筛选，例如“2020 年后科幻”“30 分钟以内”“最近新增短剧”。
- 筛选结果区显示当前条件摘要，并支持逐项删除。

### 搜索

当前搜索框视觉已改善，后续重点应从样式转向效率：

- 保存最近 10 个有效搜索词。
- 支持 `Ctrl/Cmd + K` 打开全局搜索。
- 支持影片名、演员、导演和私人标签。
- 无结果时提供清除筛选、浏览全部分类和年度榜单入口。
- 支持保存常用搜索条件。
- 移动端搜索不应隐藏在汉堡菜单深处。

私人站不需要立即建设复杂推荐或搜索集群。优先复用现有数据查询；只有真实慢查询证明确有需要时，再评估 MySQL FULLTEXT 或单独搜索索引。

### 详情页

当前详情页已经完成的正确方向：

- 播放与收藏相邻。
- 下载和评论不再进入主操作区。
- 评分、点赞和点踩已压缩为一行。
- 元数据、选集和相关推荐已经具备基本结构。

后续优化：

- 有历史时，主按钮显示“继续第 8 集 · 48:02”。
- 默认定位到上次线路和剧集。
- 长简介提供展开和收起。
- 移动端缩小海报，让播放按钮更早出现。
- 隐藏缺失字段和无效评分，避免大量“待更新”和“0.0”。
- 相关推荐增加同演员、同导演、同标签、未看同系列。
- 如果仅有一个私人用户，可以删除顶踩；保留“我的评分”和“看过”更有价值。

## 六、播放器体验

当前播放器评分：**68 / 100**

| 能力             | 当前情况                                | 主要问题                                      |
| ---------------- | --------------------------------------- | --------------------------------------------- |
| 基础播放与全屏   | React 内直接挂载 Artplayer/HLS          | 实际质量仍依赖具体播放源                      |
| 安全试看         | React 媒体入口当前拒绝仅试看权限        | 无 iframe 试看仍需服务端媒体裁剪或分片代理    |
| 快进快退         | Artplayer 热键与移动手势统一处理        | 尚未形成站点级快捷键说明                      |
| 上一集、下一集   | React 播放页已经提供                    | 尚未与完成状态和推荐下一集联动                |
| 自动连播         | 已实现                                  | 缺少完成阈值和异常处理                        |
| 播放记录         | 进入、暂停和结束会保存                  | 播放过程中缺少周期性保存                      |
| 断点续播         | Artplayer 本地恢复，数据库可存位置/时长 | 历史 DTO 不返回数值位置，跨端续播尚未完成     |
| 进度保存         | 直接读取播放器 video 状态               | 播放中关闭页面可能丢失最近进度                |
| 倍速、清晰度     | 倍速已统一；清晰度依赖播放源            | 没有统一清晰度能力检测和入口                  |
| 字幕             | 依赖播放源                              | 没有统一轨道状态和偏好                        |
| 多线路           | 有来源、剧集和失败提示                  | 缺少线路健康状态和自动换线                    |
| 画中画、影院模式 | Artplayer 支持画中画和网页全屏          | 产品层尚未形成独立影院模式                    |

### P0：完善直接播放器进度协议

React 已能直接读取 Artplayer 的 `video` 状态，不再需要 iframe `postMessage`。后续应统一处理：

- `ready`
- `timeupdate`
- `pause`
- `ended`
- `error`
- `durationchange`
- `ratechange`
- `qualitychange`

父页面需要：

1. 每 15–30 秒节流保存一次。
2. 在暂停、切后台、关闭页面和播放结束时立即保存。
3. 让历史 API 返回 `positionSeconds`、`durationSeconds` 和完成率。
4. 大于 30 秒且小于 95% 时自动续播。
5. 达到 95% 后标记看完，并推荐或自动进入下一集。
6. 登录后以云端记录为准；首次登录可以合并本地记录。

### 后续播放器能力

- 空格播放或暂停。
- 左右方向键快退或快进。
- `M` 静音，`F` 全屏。
- `N/P` 或明确按键切换剧集。
- 仅在来源支持时显示倍速、字幕和清晰度。
- 当前线路失败时展示其他可用线路，不只提供报错入口。
- 增加播放器就绪、首帧、缓冲、错误和线路切换的可观察指标。

不建议马上重写整个播放器。应先建立播放器适配层和消息协议，再逐步统一能力。

## 七、视觉与交互设计

### 当前优点

- 暗色影院风格适合私人视频场景，无需为了完整性强行增加亮色模式。
- 紫色、青色和深色背景已经形成稳定识别。
- 搜索框描边、按钮与圆角的一致性已经改善。
- 海报比例、加载占位和响应式基础较好。
- GSAP 和加载动效方向合理，并尊重减少动态效果设置。

### 当前问题

- 大标题、英雄区和玻璃卡片过多，装饰性强于信息效率。
- 所有模块都使用渐变、边框和圆角，层级趋同。
- 英文装饰文字和频道代码对中文私人站帮助有限。
- 局部次级文字与玻璃背景对比度偏低。
- 横向海报轨道依赖主动滑动，移动端下一项可发现性不足。
- 三套完整主题增加 CSS 和多端验收成本。
- React 仍整体引入旧主题 CSS，源码层样式合计约 185KB，设计系统存在耦合。

### 优化方向

- 使用 8px 间距体系。
- 每页只保留一个明确主操作。
- 用背景层级、排版和间距区分模块，减少玻璃卡片数量。
- 进度和时间使用等宽数字，正文保持 16px 以上。
- 常规状态动画控制在 150–250ms。
- 数据到达后快速退出加载状态，不等待装饰动画完整播放。
- 保留默认主题和可选主题，但所有主题共享语义化颜色和组件尺寸。

## 八、个人资料库能力

### 收藏

当前收藏支持查看、批量删除和清空，但最多返回 100 条，缺少：

- 搜索。
- 排序。
- 标签和片单。
- 更新状态。
- 观看进度。
- “下一部看什么”或“下一集”入口。

建议排序维度：

- 最近收藏。
- 最近更新。
- 标题。
- 观看进度。
- 尚未观看。

### 历史和继续观看

当前登录历史最多 100 条，本地历史最多 50 条；首页最多展示 4 条。账号历史返回的是格式化文字，没有数值进度和完成状态。

需要补充：

- 数值进度、总时长和百分比。
- 剩余时间。
- 在看和已看完分组。
- 继续观看单条隐藏。
- 跨设备同步。
- 本地历史和云端历史的一次性合并。
- 记录分页或游标，不再依赖固定上限。

### 私人标签和智能分类

不应把私人标签写入 MacCMS 公共 `vod_class`。建议新增轻量个人数据层：

| 数据结构           | 主要字段                                                                                |
| ------------------ | --------------------------------------------------------------------------------------- |
| `user_vod_state`   | `user_id`、`vod_id`、收藏时间、观看状态、最后线路、剧集、位置、时长、个人评分、更新时间 |
| `user_tag`         | `tag_id`、`user_id`、名称、颜色、排序                                                   |
| `user_vod_tag`     | `user_id`、`vod_id`、`tag_id`                                                           |
| `smart_collection` | `user_id`、名称、筛选条件 JSON、排序、系统预设标识                                      |

智能片单示例：

- 本周新增。
- 未看。
- 看到一半。
- 收藏后有更新。
- 2020 年后的高分科幻。
- 短于 30 分钟。
- 仅剩一集。
- 海报或元数据不完整。

私人用户数量少，不需要复杂推荐模型。第一阶段可以使用明确规则和保存筛选，结果更可解释，也更容易维护。

## 九、后台内容管理效率

现有 `addons/videolint/` 已经具备缺失字段、播放源、封面和重复数据扫描能力，应优先复用，而不是重建一套检查系统。

建议建设“媒体健康中心”：

- 缺失海报、背景图、年份、简介和时长。
- 缺失或空播放源。
- 重复标题和年份组合。
- 失效海报代理地址。
- 线路最后检查时间和错误原因。
- 分类、年份和筛选配置漂移。
- 最近采集和更新失败。
- 批量操作预演、审计日志和恢复说明。

采集完成后的后台任务建议依次执行：

1. 规范化类型、年份、语言和剧情。
2. 检测重复内容。
3. 生成或刷新海报规格。
4. 刷新分类和筛选快照。
5. 将片源加入健康检查队列。
6. 输出本次采集质量报告。

危险的批量修复必须保留预演、备份和明确的应用步骤。

## 十、性能分析

### 本次浏览器观察

- 片库单次加载观察到 62 个资源请求，其中 45 个为 `fetch`。
- 大量 `fetch` 来自可见筛选链接的自动路由预取。
- 内容接口单次观察约为 1.3–1.7 秒。
- HTML 可以较快出现，但主要内容仍需要客户端再次请求。
- 本次观察到一条豆瓣海报代理地址返回 404。
- 图片已有懒加载和尺寸占位，但没有统一响应式规格。

### 前端优化

- 筛选、年份和分页链接设置 `prefetch={false}`。
- 首页和片库公共数据由服务端预取并注入 Query Cache。
- 会话、收藏和历史等私有数据继续在客户端加载。
- 海报生成小、中、大规格，使用 `srcset` 和 `sizes`。
- 将 GSAP 限制在需要状态转换的页面中。
- 渐进拆分 React 设计令牌和旧主题样式，不进行一次性大重构。
- 首屏图片失败时必须显示稳定占位，并记录原始地址和代理错误。

### 后端优化

- 对内容总数、列表和筛选查询执行 `EXPLAIN`，根据真实慢查询补索引。
- 分类和筛选快照在采集后后台刷新。
- 缓存键继续包含内容权限组，避免跨权限复用。
- 历史接口返回数值进度、时长和完成状态。
- 深分页增加游标模式，保留页码兼容入口。
- API 指标拆分为权限、总数、列表、筛选和数据映射耗时。

### 服务器目标

当前没有实时资源数据，不能判断现有服务器是否不足。私人站通常只有 1–3 台设备并发，重点是稳定余量而不是高并发扩容。

需要监控：

- Next.js 进程 RSS。
- PHP-FPM 活跃进程和队列。
- MySQL 慢查询。
- 数据库、日志和图片缓存磁盘占用。
- API p50 和 p95。
- 海报代理失败率。
- 播放器首帧、缓冲和错误率。

如果 Next.js、PHP 和 MySQL 同机，维护目标可先设为至少 2 核、4GB 内存、2GB 交换空间和 20% 以上磁盘余量。该数字不是当前服务器事实。

## 十一、技术架构建议

### 当前架构

- 前端：Next.js App Router、React、TanStack Query。
- 后端：MacCMS 和 PHP。
- API：`pingfangapi` 作为同源、白名单化、权限受控的适配层。
- 数据库：MacCMS 内容表、用户表和 Ulog。
- 播放器：受控 MacCMS 原生播放器页或直链视频。
- 图片：远程海报和代理地址。

当前渐进式架构适合长期维护。无需因为视觉和交互优化而：

- 重写 MacCMS。
- 拆分微服务。
- 默认引入 Elasticsearch。
- 把真实播放地址提前下发到前端。
- 用演示数据替代真实会话和权限。

真正缺失的边界是：

1. 播放器与 React 页面之间的状态通信。
2. 公共影片元数据与个人资料库状态之间的数据模型。

### 阶段 1：低成本优化，0–6 周

- 修复筛选预取风暴。
- 压缩片库筛选。
- 修复年份和分类语义。
- 首页继续观看前置。
- 隐藏 0 分和无效字段。
- 增加播放器进度通信和数值历史接口。
- 建立 API、图片和播放器基础监控。

### 阶段 2：结构优化，2–4 个月

- 增加 `user_vod_state`、标签和智能片单。
- 收藏和历史增加游标分页。
- 首页和片库公共数据服务端预取。
- 建立分类和筛选快照。
- 渐进拆分 React 样式与旧主题样式。
- 复用 `videolint` 建立后台媒体健康页。

### 阶段 3：长期升级，4–6 个月

- 建立统一播放器适配层。
- 统一倍速、字幕和清晰度能力检测。
- 增加线路失败恢复。
- 完成跨设备续播和用户偏好同步。
- 评估 PWA 安装体验。
- 后台任务化处理海报、元数据、重复项和线路健康。

## 十七、统一验收标准

产品验收指标不以访问量为目标，而以私人长期使用效率和可靠性为目标：

- 从首页继续播放不超过 1 次点击。
- 断点续播误差不超过 10 秒。
- 登录设备间历史同步不超过 30 秒。
- 收藏和历史超过 100 条仍可完整访问。
- 已知影片在 10 秒、3 次操作内找到。
- 片库筛选不再产生批量路由预取。
- 热缓存下内容接口 p95 目标低于 500ms。
- 首屏海报不存在空白或破图。
- 390px 页面无横向溢出，筛选和播放器可单手操作。
- 播放完成状态、自动连播和下一集行为一致。
- 连续使用 30 分钟无控制台错误、进度丢失或重复记录。
- 所有账户和播放写操作继续通过同源会话、CSRF 和服务端权限校验。

每个功能完成后至少验证：

- 桌面 1440px。
- 移动端 390px。
- 加载、空数据、错误和无权限状态。
- 键盘、焦点和减少动态效果。
- 匿名、本地记录和登录账号记录。
- 真实 staging API、Cookie 和播放器权限。

不能用本地 fixture、页面 HTTP 200 或构建成功替代真实业务验收。
